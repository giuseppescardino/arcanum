# Browser extension (Chrome, Opera, Safari) — design

Status: approved 2026-11-11; revised the same day after the branch review (commit-then-reveal pairing, typed code, capture rules, key storage). The as-built threat model is in `docs/SECURITY.md` → "Browser extension".

## Goal

A browser extension for Chrome, Opera and Safari that, while the user browses:

1. **fills** saved logins into login forms;
2. **suggests** a strong generated password on sign-up / change-password forms;
3. **saves** new logins (or updates a changed password) after a form is submitted.

## Decisions

- **Source of truth is the desktop app.** The extension holds no vault data and no vault keys. Every credential comes from the running, unlocked Arcanum app on macOS or Windows. Unlocking (password or biometrics), sync and encryption at rest stay in the app and the Rust core.
- **Transport is loopback HTTP with end-to-end encryption, not native messaging.** The app listens on `127.0.0.1` only. A sandboxed macOS app cannot install native-messaging manifests into Chrome/Opera profile folders, and a native host would still have to authenticate its caller, because any local process can launch it. Confidentiality and authenticity come from a 256-bit key agreed at pairing, not from TLS. A self-signed certificate on loopback would be rejected by browsers unless a CA were installed system-wide, which is worse.
- **Pairing is opened from the app and confirmed in the app** with a code derived from an ephemeral X25519 exchange. X25519 rather than P-256: `p256` 0.13 would bring crypto-bigint 0.5 (RUSTSEC-2026-0387, non-constant-time) onto a live path, and Arcanum already relies on Curve25519 for OPAQUE. WebCrypto supports X25519 from Chrome/Opera 133 and Safari 17.
- **One extension source for all three browsers.** Plain JavaScript, Manifest V3, no build step. Every script is a classic script sharing `globalThis.Arcanum` (the background loads `lib/` with `importScripts`): Safari runs neither module service workers nor module content scripts, and loading modules from a content script would make extension files web-accessible to pages. Shipped files live in `extension/src/`. Safari gets a small Xcode wrapper project generated by `safari-web-extension-converter` that references the same files.

## Components

| Unit | Purpose | Depends on |
|---|---|---|
| `core/arcanum-bridge` | Pairing math (X25519, HKDF-SHA256, verification code), message envelope (AES-256-GCM), replay window. No I/O. | `x25519-dalek`, `aes-gcm`, `hkdf`, `sha2`, `rand_core`, `zeroize` |
| `core/arcanum-ffi/src/api/bridge.rs` | Dart-facing wrappers of the bridge crate. | `arcanum-bridge` |
| `app/lib/browser/bridge_server.dart` | `HttpServer` on `127.0.0.1`: origin/host checks, pairing state machine, decrypts requests and encrypts replies. | FFI bridge, `BridgeClients`, `BridgeHandler` |
| `app/lib/browser/bridge_handler.dart` | Executes a decrypted request against `VaultController` (list, fill, generate, check, save, update). Pure Dart, unit-tested with fakes. | `VaultController`, `matching.dart` |
| `app/lib/browser/bridge_clients.dart` | Paired browsers: id, name, key, creation date, kept in the system keychain (`flutter_secure_storage`). | `flutter_secure_storage` |
| `app/lib/ui/browser_pairing.dart` | "Browser collegati" screen: start pairing, verification dialog, list, revoke. | the above |
| `extension/src/` | MV3 extension: `background.js` (transport, crypto, pairing, routing), `content/ui.js` (field detection, inline menu, save banner), `popup/`, shared classic scripts in `lib/`. Tests and sample pages in `extension/test/`. | WebCrypto, IndexedDB |
| `extension/safari/` | Xcode wrapper app + Safari Web Extension target, generated once and committed. | `extension/src/` files |

Mobile platforms (Android, iOS) do not start the server.

## Protocol

All requests are `POST http://127.0.0.1:<port>/v1` with a JSON body. The app tries ports 47613, 47614, 47615 in order and the extension probes the same list. It remembers the last one that answered.

### Request filtering (before any parsing of the payload)

- `Host` header must be `127.0.0.1:<port>` (DNS-rebinding defense).
- `Origin` header, if present, must start with `chrome-extension://` or `safari-web-extension://`. Anything else gets `403` (web pages).
- Body at most 64 KiB, `Content-Type: application/json`.
- Replies to extension origins carry `Access-Control-Allow-Origin: <origin>`. Nothing is sent for other origins.

### Plain messages

- `{"type":"hello"}` → `{"app":"arcanum","protocol":1,"pairing":true|false}`. This reveals only that the app runs and whether a pairing window is open.
- `{"type":"pair_start","name":"Chrome","commit":"<b64 SHA-256(\"pm/bridge-commit/v1\" ‖ ext_pub ‖ nonce32)>"}` returns one of:
  - `403 pairing_closed` if no pairing window is open;
  - `409 pairing_busy` if another pairing is pending;
  - otherwise `{"pairing":"<id>","pub":"<b64 raw 32-byte X25519 app key>"}`.
- `{"type":"pair_reveal","pairing":"<id>","pub":"<b64 ext_pub>","nonce":"<b64 32 bytes>"}` → `{}` once the app has checked the reveal against the commitment and derived key and code; then the app shows the pairing dialog. Any mismatch → `400` and the pairing is rejected.
- `{"type":"pair_status","pairing":"<id>"}` → `{"state":"pending"}` | `{"state":"approved","client":"<client id>"}` | `{"state":"rejected"}`.

### Key derivation (both sides)

```
shared = X25519(ext_priv, app_pub) = X25519(app_priv, ext_pub)    (32 bytes; all-zero result rejected)
th     = SHA-256("pm/bridge-pair/v1" ‖ ext_pub ‖ app_pub)
key    = HKDF-SHA256(salt = th, ikm = shared, info = "pm/bridge-key/v1", 32 B)
code   = HKDF-SHA256(salt = th, ikm = shared, info = "pm/bridge-code/v1", 4 B) as big-endian u32 mod 1 000 000, 6 digits
```

The browser commits to its key before it learns the app's, so a man in the middle cannot search keys for a matching code. The browser shows the code and the user **types it into the app**, which never displays it; three wrong codes reject the pairing. Rejecting, closing the dialog or waiting 120 s ends the pairing. The pairing window (opened by "Collega browser") lasts 120 s and accepts a single pending pairing. When approved, the app generates a random 16-byte `client` id (base64url) and stores `{client, name, key, created}` in the keychain. The extension stores `{client, key}` with the key as a non-extractable WebCrypto key in IndexedDB of its own origin.

### Encrypted messages

Request: `{"type":"msg","client":"<id>","ct":"<b64(nonce12 ‖ ciphertext ‖ tag16)>"}`

- AES-256-GCM with `key`, random 96-bit nonce.
- AAD = `"pm/bridge-req/v1" ‖ client` for requests and `"pm/bridge-res/v1" ‖ client` for responses, so a request cannot be replayed as a response or vice versa.
- Request plaintext: `{"id":"<random 16 B b64>","ts":<unix ms>,"body":{...}}`.
- The app rejects requests with `|now − ts| > 60 s` or an `id` already seen in that window (`400 replay`).
- Response plaintext: `{"id":"<request id>","body":{...}}`. The extension discards a response whose `id` differs from the request's.
- Unknown `client` → `401 unknown_client` in clear: the extension forgets its pairing and offers to pair again.

### Bodies

| Request `body` | Response `body` |
|---|---|
| `{"op":"status"}` | `{"locked":bool}` |
| `{"op":"open_app"}` | `{}` (window brought forward) |
| `{"op":"list","url":U}` | `{"logins":[{"id","title","username"}]}`, only items whose URLs match `U`'s host |
| `{"op":"fill","id":I,"url":U}` | `{"username","password"}`, or `{"error":"domain_mismatch"}` if item `I` does not match `U` |
| `{"op":"generate"}` | `{"password"}` (core generator: 20 chars, all sets, avoid ambiguous off) |
| `{"op":"check","url":U,"username":N,"password":P}` | `{"state":"new"}` \| `{"state":"update","id"}` \| `{"state":"same"}` |
| `{"op":"save","url":U,"username":N,"password":P}` | `{"id"}`, a new login titled with `U`'s host and URL `https://<host>` |
| `{"op":"update","id":I,"url":U,"password":P}` | `{}`, or `domain_mismatch` |

Every op except `status`, `open_app` and `generate` returns `{"error":"locked"}` while the vault is locked. Host matching reuses `hostsMatch` from `app/lib/autofill/matching.dart` (same host, or subdomain on a label boundary). `U` always comes from the browser's tab URL as seen by `background.js` (`sender.tab.url`), never from the page.

## Extension behavior

- **Field detection** (`lib/forms.js`, pure functions over element attributes):
  - password field = `input[type=password]` that is visible;
  - username field = the closest preceding visible text/email input in the same form, preferring `autocomplete=username|email` and name/id hints such as `user`, `email` or `login`;
  - new-password context = `autocomplete="new-password"`, or two or more password fields in the form, or hints such as `signup`, `register`, `confirm` or `new`.
- **Inline menu**: on focus of a detected field, a small Arcanum icon appears inside the field (shadow DOM, so the page's CSS cannot restyle it). Clicking the icon opens a menu:
  - login context: matching logins, or "Sblocca Arcanum" when locked, or "Nessuna credenziale per questo sito";
  - new-password context: "Usa password sicura" with the generated value masked; clicking fills every password field of the form.
  - Fill sets `value` through the native setter and dispatches `input` and `change`, so frameworks notice.
- **Save**: on `submit`, on Enter in a password field, or on a click on a formless button that reads like log in / sign up, the content script sends `{username, password}` to the background. Only events with `isTrusted` and a recent user gesture count; buttons inside a form are left to its submit event. The background asks `check` (usernames compared case-insensitively; an empty username updates the site's only login, or matches any login with that password):
  - `same` → nothing;
  - otherwise the pending entry is kept per tab in `chrome.storage.session` for 120 s, and the content script of the current or next page in that tab shows a banner: "Salvare la password per <host>?" or "Aggiornare la password per <user>?", with *Salva/Aggiorna* and *Non ora*.
  - A locked vault at banner time shows "Sblocca Arcanum" in the banner.
- **Popup**: connection state (app not running / not paired / locked / ready), pairing flow (shows the 6-digit code), matching logins for the current tab with *Compila*, and the generator with *Copia*.
- **Scope limits (v1)**: top frame only (`all_frames: false`); no fill on page load; no cards, TOTP or other item kinds; no credentials from other domains (the user opens the app for those).

## Error handling

| Situation | Behavior |
|---|---|
| App not running (no port answers) | Popup and menu say "Avvia Arcanum". |
| Vault locked | `locked` → "Sblocca Arcanum" (sends `open_app`). |
| Pairing revoked in the app | `unknown_client` → the extension clears its key and shows "Collega". |
| Bad ciphertext, replay, wrong `id` | Request dropped; the extension shows a generic error. |
| Port taken by another process | The app tries the next port. If all fail, "Browser collegati" shows the error. |

## Testing

- **Rust** (`arcanum-bridge`): both sides derive the same key and code; tampered ciphertext, wrong AAD direction, wrong key and replayed id are rejected; ts window.
- **Interop**: a Rust test writes fixed-input vectors (keys, code, ciphertext) to `extension/test/vectors.json`, and `node --test` checks that the WebCrypto code reproduces them.
- **Dart**: `BridgeHandler` against a fake vault (locked, list matching, fill mismatch, check states, save, update); `BridgeServer` on a real loopback socket (origin/host rejection, pairing flow, encrypted round trip, unknown client).
- **JS**: `node --test` for `lib/forms.js` heuristics (on plain attribute objects), `lib/url.js` and the crypto module.
- **Manual**: load unpacked in Opera Air (Chromium) and in Safari (unsigned extensions allowed), with the app running: pair, fill, generate, save, update, revoke.
